Define and customize agent roles

Roles package a reusable agent policy: model, thinking level, tools, skills, extensions, prompt instructions, and context-file scope. Use a role file for stable defaults, then use per-call AgentOptions to override model, thinking, capabilities, and context files.

This is the workflow/subagent consumer guide. The standalone @piewf/pi-ext-roles roles guide, linked from its README and shipped with the package, owns role authoring, shared configuration, contribution/resolution APIs and native CLI behavior. No workflow installation is required to use those independent features.

Overview

A workflow agent selects a role by name. The role body always comes from the named file. Per-call AgentOptions override the role-file defaults.

const plan = await agent("Plan the implementation", {
  role: "planner"
});

const fastReview = await agent("Review this change", {
  role: "reviewer",
  model: "cheap-model",
  contextFiles: ["cwd"],
  tools: ["!*", "read", "grep"]
});

Per-call model, thinking, tools, skills, extensions, and contextFiles override role-file defaults. Role extensionSettings replaces declared top-level namespaces while retaining omitted ones. Built-in subagent tools discover these same role files and apply the same validation to standalone agent runs.

Launch Pi with a role

pi-role belongs to @piewf/pi-ext-roles. It composes role arguments and launches the native pi executable from PATH, without requiring workflows or creating an SDK session first. The independent package is published as @piewf/pi-ext-roles@0.1.2; workflow major publication remains subject to the release gate.

npm install -g @piewf/pi-ext-roles
pi-role --list
pi-role reviewer
pi-role scout -p "Where is the retry logic?"
pi-role reviewer --approve
pi-role --version # no role: stock Pi

Selected sessions use native Pi interactive, print/JSON, RPC, help, model and session behavior. Explicit models are passed to Pi without launcher catalog validation or role fallback; known providers may accept custom model IDs. Role/shared aliases are composed before spawn. Dynamic contributor discovery is not a CLI feature: list and launch use static role files. Extension and skill selectors filter metadata before spawn, so selected-out factories never load; help also suppresses factories.

Role/shared tool selectors set the model-declared loadout through a tiny explicitly loaded tools bridge. They do not revoke deferred or codemode capabilities. Native --tools overrides that loadout within its registry allowlist; --exclude, --no-tools and --no-builtin-tools remain hard ceilings, including after reload and attempted re-enablement. Wildcards are native registry selectors, not factory discovery.

The native CLI supports only all context scopes or []. Partial contextFiles scopes fail explicitly unless native --no-context-files suppresses context. Empty --system-prompt retains native default-prefix semantics. Shared and role extensionSettings are deliberately not applied by the binary.

The independent discoverRoles, resolveRole and composeRoleConfiguration APIs return definitions and resolved options only. They do not create SDK sessions, load extension factories, own snapshots or disposal, or deliver a special settings event channel. Workflow and subagent consumers apply model, tools, prompt, context scopes, skills and extensions through their existing runtime. Workflow itself transports extensionSettings through its consumer session/start/hook seam, including session_start event.settings. Session creation, provider loading, recovery snapshots and lifecycle remain workflow responsibilities.

Migrate roles

The extraction is planned for the next workflow major release because the contributor registration contract changes. Updating workflows supplies the independent roles library through its dependency: workflow/subagent users do not need a separately installed or enabled roles plugin. The independent package is published and the isolated upgrade from 5.19.1 to the major candidate is verified. Workflow major publication is still pending; see the agreed release and upgrade checklist.

The independent fallback roles do not select a model or provide workflow-specific aliases. If you relied on an old fallback model, set an explicit per-call model or create a global/project role with the same name, preserving its prompt body and adding the desired model; define any shared alias in the new roles settings. Existing consumer settings remain overrides, but they do not restore a removed fallback role's model field automatically.

Move global role files from ~/.pi/agent/pi-extensible-workflows/roles/ to ~/.pi/agent/pi-ext-roles/roles/, and project roles from .pi/pi-extensible-workflows/roles/ to .pi/pi-ext-roles/roles/. Move shared aliases, tools, skills, extensions and extensionSettings to the corresponding pi-ext-roles/settings.json. Workflow settings remain explicit consumer overrides; the independent package never reads them. Project aliases replace the entire shared global alias map, including {}. Selector order is shared global/project, consumer global/project, role, call, bounded by consumer resources and parent tool ceilings.

No files are rewritten automatically. Workflows temporarily retain old role parser/resolver imports and legacy filesystem paths, not role registration. registerWorkflowExtension({ roleDirectories }) fails with INVALID_METADATA and migration guidance, with or without source. Remove that field and register roles separately with registerRoleContribution(pi, { owner: import.meta.url, roleDirectories: ["./roles"] }) from @piewf/pi-ext-roles. registerWorkflowExtension takes one argument; source remains supported for workflow function provenance and portable bundling. Re-export portable bundles that used the removed registration field.

Legacy directories are visible to programmatic role consumers only when an authorized workflow consumer contributes those paths; the native CLI does not collect dynamic contributions and requires migration to the new paths; the independent package does not discover workflow paths on its own. The workflow integration emits one migration warning per TUI session when actual legacy role files or shared role settings fields are present, even without a selected role. Empty directories and non-TUI modes do not produce warnings; protected project sources are inspected only after explicit trust. Warnings and legacy path contributions require loading the workflow integration, which the independent package never loads on its own. No removal date for the remaining import/path compatibility or automatic migration is scheduled.

Upgrade a global @piewf/cli installation before installing the independent package so the old CLI no longer claims pi-role: npm install -g @piewf/cli, then npm install -g @piewf/pi-ext-roles after publication approval. Do not force-overwrite a conflicting binary from an older CLI. @piewf/cli/pi-role still forwards runPiRole; the deprecated piArguments/resolvePiArguments imports remain isolated legacy argv projections. They do not execute extension factories or discover contributor SDK startup state; tool enumeration is limited to Pi builtins. Partial context scopes, effective extensionSettings, and unavailable extension tool projection throw instead of being silently ignored. Models are validated without alias fallback. Use runPiRole for native CLI startup; it never calls these helpers. Use the independent option-producing APIs with a consumer runtime, such as workflow or subagents, when settings delivery or partial context scopes are required.

Standalone roles API

The independent @piewf/pi-ext-roles/roles subpath (with the old pi-extensible-workflows/roles entrypoint retained as a workflow compatibility adapter) exposes role discovery without creating a workflow or host. Use discoverRoles({ cwd, agentDir, projectTrusted, extensionRoleDirectories }) to load the active definitions, loadRole(name, options) to load one validated role, and resolveRole(name, options) to obtain its effective model, prompt mode, context scopes, selector layers, selected resources, and unmatched selectors. Optional resources, rootTools, knownModels, availableModels, and modelAliases provide the runtime boundaries needed for matching and model resolution; without them, selector layers are returned, while selected resources and tools remain unknown rather than being inferred.

Role files

Global roles live under <agentDir>/pi-ext-roles/roles/<name>.md, normally ~/.pi/agent/pi-ext-roles/roles/<name>.md. Set PI_CODING_AGENT_DIR to change the agent directory.

Trusted project roles live under <cwd>/.pi/pi-ext-roles/roles/<name>.md. A trusted extension contributes packaged roles with registerRoleContribution(pi, { owner: import.meta.url, roleDirectories: ["./roles"] }) from @piewf/pi-ext-roles. Relative directories resolve from the owner. Role precedence is fallback roles < contributors < global < authorized project; within one scope, new paths override legacy paths. Starter roles are low-precedence fallbacks, so a regular extension role silently overrides a starter role with the same name; duplicate names among regular extension roles are rejected. The bundled starter roles follow that rule; see Bundled starter for aliases, reviewLoop, and how to disable the factory.

---
description: Reviews code for correctness
model: anthropic/claude-fable-5:high
tools: ["!*", read, grep]
skills: ["!*", "review-*"]
extensions: ["!**/unsafe.mjs"]
---
Focus on correctness and regressions.

The body is prompt guidance. It is appended to the native Pi system prompt unless overrideSystemPrompt: true is set. Role files are trusted configuration and can affect model, tools, resource selectors, extension settings, and the system prompt.

Frontmatter fields

FieldPurpose
descriptionRole description shown in role discovery and Pi guidance.
modelConfigured alias or concrete provider/model:thinking.
tools, skills, extensionsOrdered Minimatch selectors. Positive patterns enable discovered candidates, !pattern disables them, later layers override earlier layers, and !* clears the current selection before narrower additions.
extensionSettingsJSON object of extension-owned namespace values. Declared top-level namespaces replace inherited values; omitted namespaces remain inherited.
overrideSystemPromptWhen true, use the role body instead of appending it to the native system prompt.
contextFilesChoose which Pi context-file scopes reach the role.

Relative extension selectors in role frontmatter resolve from the role file's directory; call-level selectors resolve from the agent launch cwd. See the settings reference for ~, file://, glob, and canonicalization rules.

Customize calls

role is a name string. Per-call model, tools, skills, extensions, and contextFiles override the role file. Concrete models are provider/model:thinking. overrideSystemPrompt stays on the role file.

await agent("Inspect the API", {
  role: "reviewer",
  contextFiles: ["cwd"],
  model: "cheap-model:low",
  tools: ["!*", "read", "grep"]
});

Use tools: ["*"] to re-enable all tools after a role restriction.

Context and resources

contextFiles controls Pi context discovery for that role. global selects the Pi agent-directory file, cwd selects the exact working-directory file, and project selects discovered project and ancestor files excluding those two. Omit the field for normal discovery or use [] to load none. Scopes can be combined.

---
contextFiles: [global, project]
skills: ["!*", "review-*"]
extensions: ["!*", "**/review-tools/**"]
tools: ["!*", read]
---

Selectors affect only agents using the role and compose after global and trusted-project selectors. Use piewf doctor --role <name> to inspect selector sources and effective skills, extensions, and tools without contacting a provider.

Inspect a role

npx -p @piewf/cli piewf doctor --role reviewer
npx -p @piewf/cli piewf doctor --role reviewer --prompt "Review the current change"
npx -p @piewf/cli piewf doctor --role reviewer --json
npx -p @piewf/cli piewf doctor ./roles/reviewer.md

The role inspection is read-only. The positional form piewf doctor reviewer is equivalent to --role reviewer. Both resolve the active role and report its effective resources and prepared prompt. A role ending in .md is read as a role file instead, relative to the current working directory, so you can check a role before installing it. The optional probe prompt is useful when prompt hooks depend on the agent request. Add --json to emit the structured report for machine consumers; either role form includes roleTarget and includes roleInspection when inspection succeeds.

Role discovery is fail-closed: invalid frontmatter or the rejected legacy selector in any packaged or global role file, or in any trusted-project role file, blocks the complete role set. See the doctor reference for diagnostics and exit behavior. At runtime, a missing named role fails with UNKNOWN_AGENT_TYPE and Unknown agent role: <name>.

See workflow tool usage, settings for model aliases and global selectors, and extension resources for packaged role directories.
